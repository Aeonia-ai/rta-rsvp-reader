# HTTPS Glasses Deployment Surface Design

## Goal

Make the RSVP reader deployable as one single-user HTTPS application with a landing route, a passive Meta-glasses route, and a browser control route.

## Scope

The production server continues to own one in-memory reader state and one existing WebSocket control endpoint. Vite serves three client-side routes from the same origin:

- `/`: a minimal landing page containing a QR code that resolves to `<current origin>/glasses-app`.
- `/glasses-app`: the current no-UI RSVP display.
- `/controls`: the desktop control console.

The control console supports only reader operations: load a bundled sample, set WPM, play, pause, stop, and inspect status. It does not expose server start, stop, or restart; deployment-process lifecycle belongs to the host platform.

## Single-user assumptions

There is one trusted user and one active reading session per deployment. No account, authentication, per-user session, database, persistence, concurrent-reader isolation, or multi-device arbitration is added. Any glasses page and controls page connected to the same origin observe the same reader state.

## Routing and transport

The existing Node HTTP server already serves the Vite bundle and upgrades `/ws` requests. It will serve the same SPA entry document for `/`, `/glasses-app`, and `/controls`; the browser chooses the route from `location.pathname`.

The glasses page remains a display WebSocket client. The controls page becomes a control WebSocket client using the existing typed commands: `set-text`, `set-speed`, `play`, `pause`, `stop`, and `status`. HTTPS hosting automatically changes the browser URLs to WSS.

## Landing page

The landing page contains only an app name, a short “Open on glasses” instruction, and a QR image. The QR payload is constructed at runtime from `new URL("/glasses-app", location.origin)`, preventing a hard-coded local or preview URL. It includes a normal link underneath for desktop testing.

The QR implementation is a browser dependency that renders a canvas or SVG locally; it makes no network call.

## Controls page

The controls page has a visible, conventional browser UI:

- Sample selector populated from a safe, static sample manifest.
- WPM selector with the supported 60–1200 range.
- Load, Play, Pause, Stop, and Refresh Status buttons.
- Read-only state summary: document, word index/total, phase, and WPM.
- Clear connection/error feedback.

The sample manifest is generated by a small server endpoint that exposes only known files in `samples/`, or by a compiled allow-list shared by server and client. The chosen implementation must never accept a file path from the browser.

Controls issue the existing WebSocket control protocol directly. After any acknowledged action, the page updates its displayed status from the returned snapshot.

## Glasses page

`/glasses-app` uses the existing reader display component and keeps its no-control behavior. It receives frame/clear messages over the same-origin display WebSocket. Its document viewport and CSS are adjusted to Meta Ray-Ban Display’s 600×600 target without introducing interactive controls.

## Deployment packaging

Add a production `Dockerfile` and concise host-agnostic deployment instructions. The Node process listens on `0.0.0.0` and honors `PORT`; it still defaults to loopback for local CLI use. A reverse proxy or managed host terminates TLS, making the pages available at public HTTPS and WebSocket traffic at WSS.

No deployment account, domain, cloud provider, secrets, database, or automatic release is created in this work.

## Validation

- Unit tests cover route selection, QR target construction, safe sample manifest, control-message handling, and glasses-page passive behavior.
- Browser tests verify the landing page link/QR target and controls UI against a local reader server.
- Existing server and RTA tests continue to pass.
- Build output works with a production server bound through `PORT`.
- Manual handoff checklist: deploy HTTPS URL, open `/`, use its QR/deep link to register `/glasses-app` in Meta Developer Mode, and control the reader from `/controls`.

## Deferred

Paired-phone VTT, model inference, authentication, multiple users, remote persistence, hosted relay authorization, and hardware-specific brightness tuning remain out of scope.
